# D2 Source Archaeology + Technical Evidence Audit

Audit date: 2026-08-30  
Source repository: the separate grant_find research checkout  
New project: this repository

## 1. Verdict

### AUDIT C — MATERIAL REPROOF REQUIRED

The central idea is technically plausible: CKB light-client storage contains
Script-derived rows that can be selected, serialized, and restored into an
already-established destination view. An earlier throwaway experiment also
used the real pinned light-client storage API and therefore provides some
useful evidence.

The committed PB1, however, does not establish D2 as proven infrastructure.
It is a standalone model with a synthetic CKB-like keyspace, synthetic
transactions and headers, a proof-local SQLite destination, and a locally
simulated replay loop. Its headline historical-replay and backend-independence
claims do not follow from the executable path. The earlier real-API importer
is stronger in one dimension but transported chain and runtime authority,
which directly conflicts with the claimed consensus separation.

This is not Audit D: nothing inspected disproves the possibility of a
properly designed Script-derived state handoff. It is Audit C because the
claims required to freeze the boundary, especially progress reconstruction,
consensus separation, real upstream continuation, crash safety, and current
consumer compatibility, remain unproven.

The research classification PROVEN PRE-BUILD INFRASTRUCTURE CANDIDATE was
therefore too strong. The accurate classification is: promising boundary,
disposable proof harness, material reproof required.

## 2. Executive technical finding

The important distinction is between three artifacts that the research
narrative treated as one result:

1. The committed D2/PB1 crate at d2-portability-proof. It has no
   ckb-light-client dependency. It creates a real RocksDB directory with a
   Java JNI helper, but populates it with rows generated by its own Rust
   fixture. It imports selected rows into a separate SQLite table implemented
   by PB1 itself.
2. The earlier D-BOOTSTRAP scratch importer at
   ckb-boundary-probes/D-BOOTSTRAP/scratch/importer. This links the pinned
   ckb-light-client library, creates real upstream Storage instances, uses
   actual upstream storage methods, and runs an offline continuation. It is
   still a four-block synthetic chain, only exercised SQLite, and imports
   LAST_STATE, genesis, checkpoints, LAST_N_HEADERS, FILTER_SCRIPTS, and
   MIN_FILTERED_NUMBER. It is not evidence of a consensus-free handoff.
3. The current Pocket Node consumer. It embeds a different vendored
   light-client tree, exposes JNI script registration, uses per-network
   RocksDB paths, and stores application state separately in Room. It has a
   credible eventual insertion point, but no D2 import API or lifecycle hook
   and currently vendors ckb-light-client 0.5.4 while the inspected upstream
   revision reports 0.5.5.

What PB1 genuinely demonstrates:

- deterministic selection of ten A rows from an 18-row synthetic source;
- exclusion of two B script-index rows and three synthetic authority rows in
  that fixture;
- deterministic canonical key/value encoding and SHA-256 of that payload;
- a SQLite transaction that rolls back on an injected in-process failure;
- a local continuation helper that reaches synthetic block 13;
- rejection of eleven deliberately generated invalid-package variants.

What it does not demonstrate:

- extraction from a genuine ckb-light-client database;
- semantic equivalence of real upstream light-client views;
- that the upstream filter scheduler will skip thirteen historical blocks
  after a handoff;
- safe reconstruction of the upstream progress markers;
- exclusion of consensus authority in a real light-client database;
- RocksDB-to-upstream-SQLite or SQLite-to-upstream-RocksDB runtime
  interoperability;
- crash/power-loss atomicity, concurrent import safety, merge policy, reorg
  behavior, version migration, or mainnet-scale viability.

## 5. D2 chronology

### 5.1 Originating observation

The observation behind D2 was soundly targeted: the light client tracks
registered Scripts and stores derived cell/transaction history in a keyspace
that is distinguishable from chain and proof state. A destination that already
has an independently established chain view may not need to replay all
historical blocks merely to reconstruct one wallet’s derived view.

The first reports framed this as snapshot/bootstrap handoff. They also
identified the correct objections: completeness, Script identity, progress
markers, reorg handling, trust boundaries, package size, import safety,
version coupling, and Pocket lifecycle.

### 5.2 Predecessor research and objections

D-BOOTSTRAP/REPORT.md describes a snapshot format and an adapter seam, while
explicitly admitting that provider completeness, deep history, reorgs, and
production integration were not proven. It then describes Probe 3 as a
real-light-client experiment.

PV1 sharpened the key objection. Upstream currently retains a per-Script
FILTER_SCRIPTS cursor plus a global minimum filtered block number, but not a
full per-Script coverage interval ledger. A single cursor cannot prove that
all blocks from a claimed start to the cursor were processed under the same
Script registration and chain history. PV1 also found that Pocket maintains
application-level progress and candidate state outside the light-client
database.

These are not minor edge cases. They determine whether a package can safely
claim “historical work avoided” rather than merely “some rows restored.”

### 5.3 Why the throwaway importer was created

The D-BOOTSTRAP scratch importer was created to move from a model to actual
upstream Storage. It:

- linked ckb-light-client-lib by path;
- initialized actual SQLite Storage;
- called init_genesis_block;
- registered a packed Script using update_filter_scripts;
- processed synthetic packed CKB blocks with filter_block;
- advanced upstream filter and state markers;
- extracted actual upstream raw rows;
- imported them through the upstream BatchWriter;
- continued with filter_block on a subsequent synthetic block.

That was the right direction. It still only exercised a tiny offline
four-block chain, one backend, and an importer that carried global authority.

### 5.4 Why final PB1 was created

The committed D2 proof appears to have optimized for a short reproducible
cross-backend and fail-closed harness. It uses the phroi kvpairs transport
model and substitutes a local logical keyspace so that the experiment can run
without building or linking the upstream light client.

Its intended proof obligations were:

- select A state from a mixed A/B source;
- omit authority rows;
- produce a portable payload;
- import into a separate SQLite destination;
- compare source, replay baseline, and imported views;
- show a continuation at block 13;
- reject eleven malformed or mismatched inputs.

The obligations are meaningful, but the implementation no longer exercises
the real system boundary.

### 5.5 Promotion decision versus evidence

The final D2 REPORT.md says PROOF SURVIVES and recommends D2 as a pre-build
infrastructure candidate. The code’s own limitations section says the
transactions and headers are synthetic, the client is not launched, the
authority model is compact and local, and the benchmark is tiny.

Those limitations are accurate. The promotion decision is not supported by
the stronger meaning assigned to “proven.” The honest conclusion from the
artifacts is a valid research direction with a disposable harness.

## 6. PB1 architecture reconstruction

The committed implementation is concentrated in:

- d2-portability-proof/src/lib.rs;
- d2-portability-proof/src/main.rs;
- d2-portability-proof/tests/reproduction.rs;
- d2-portability-proof/scripts/RocksRows.java;
- d2-portability-proof/scripts/reproduce.ps1 and reproduce.cmd.

The end-to-end path is:

    make_fixture
      -> write_rocks_source
      -> Java RocksDB put/iterate bridge
      -> extract_script_rows
      -> encode_kvpairs
      -> JSON manifest + payload.kvpairs
      -> load_and_validate_package
      -> SQLite kv_store transaction
      -> local append_verified_block

There is no upstream light-client process in this path.

### 6.1 Source database/backend

Physically, write_rocks_source creates a genuine RocksDB directory and the
Java helper opens it with RocksDB JNI. That part is not a mock file.

Semantically, it is not a genuine ckb-light-client database. The Rust code
constructs the rows itself. It uses a subset of the upstream-looking prefix
numbers and values, but it does not call ckb-light-client Storage, its
Key/Value encoders, filter_block, chain verifier, or its RocksDB backend.

The transaction values are explicitly synthetic. They begin with block and
transaction coordinates followed by a synthetic-ckb-tx tag. The block and
genesis hashes are SHA-256 values of strings such as d2-pb1-block-N. No CKB
packed transaction or header is being persisted.

The source therefore is:

- a real RocksDB container;
- a PB1-created logical KV representation;
- not a real upstream light-client database.

### 6.2 Destination

SqliteDestination creates three PB1-owned tables:

- kv_store;
- authority_state;
- verified_headers.

The authority tables are not upstream SQLite storage tables. The destination
is initialized with an AuthorityState supplied by the test, already at the
handoff tip. The importer then inserts only selected kv_store rows.

This is a useful model of physical separation. It is not a destination
ckb-light-client instance.

### 6.3 No production dependency

Cargo.toml proves that PB1 does not compile against ckb-light-client.
evidence/UPSTREAM-REVISIONS.txt records upstream revisions as inspection
references only. The production upstream APIs are therefore not part of the
executable proof.

## 7. Exact Script identity model

### 7.1 PB1 identity

PB1 represents a selector as:

- script: a hexadecimal byte string;
- script_type: lock or type.

ScriptSelector::raw_script accepts a string beginning with 0x and decodes
arbitrary bytes. It does not parse a Molecule packed Script. It does not
calculate or store a Script hash. It does not separately represent code_hash,
hash_type, and args.

The fixture’s A selector is a 32-byte repeated 11 value followed by 00a1.
The B selector is a 32-byte repeated 22 value followed by 01b2. They are
same-length artificial byte strings.

The manifest also binds:

- network = d2-fixture-net;
- a synthetic genesis hash;
- handoff block number and hash;
- script bytes and role.

The network and genesis are package metadata, not part of the key identity.
The start block is not part of Script identity. No internal light-client
Script ID or index is used.

### 7.2 Matching weakness

extract_script_rows and validate_script_isolation use a prefix test:
the bytes after a family prefix must start with the raw Script bytes.
They do not validate the exact Script boundary or parse the suffix according
to the upstream key grammar.

That permits aliasing if one valid Script byte sequence is a prefix of
another valid Script sequence in the same family. The fixture does not expose
this because A and B differ immediately and have equal lengths. The tests
also do not use a pair designed to trigger prefix aliasing.

The implementation also assumes the first byte family and fixed value
shapes are enough to establish ownership. It does not cryptographically
validate transaction hashes against transactions, block hashes against
headers, or transaction/header relationships.

### 7.3 Upstream identity

At the inspected upstream revision, the true registration identity is a
packed Script plus ScriptType, with a caller-supplied start block. A packed
Script contains code hash, hash type, and args; the role is separate. The
keyspace itself does not contain network identity. Network/genesis and
consensus state are external to the Script key.

Thus “exact Script” is only partially established by PB1. The predecessor
used actual packed Script matching more faithfully, but its extraction still
used byte-slice selection and did not solve completeness or versioning.

## 8. Exported and excluded state

### 8.1 Final PB1 exported categories

| Category | PB1 representation | Why it is selected | Leakage/omission assessment |
|---|---|---|---|
| Script index rows | Artificial cell and transaction-history prefixes for A | Key bytes start with the selected raw Script and role family | B index rows are excluded in the fixture; exact boundary and real upstream value semantics are not validated |
| Transaction facts | TxHash-family rows with synthetic block/tx coordinates and synthetic bytes | Referenced by selected Script rows | Shared transaction data can legitimately support more than one Script; PB1 does not prove complete closure or real transaction ownership |
| Block facts | BlockNumber to hash and BlockHash to nonempty header fact | Needed by the local transaction-to-header lookup | Hash/header and number/hash consistency are only shallowly checked |

The fixture’s selected output is four script-index rows, four block-fact
rows, and two transaction-fact rows: ten rows total.

### 8.2 What the final PB1 source contains

The 18 source rows are reported as:

- six block facts;
- six script-index rows;
- three transaction facts;
- three consensus_or_shared_authority rows.

The three authority rows are synthetic LAST_STATE, checkpoint, and
FILTER_SCRIPTS data. They are not a complete upstream authority set.

### 8.3 Excluded state

The package manifest excludes LAST_STATE, checkpoints, FILTER_SCRIPTS, and
peer/network state. The final importer writes no authority rows and does not
change destination authority.

That is a good desired boundary for a destination-owned-consensus design, but
PB1 never demonstrates the boundary against a real upstream database. In
particular, excluding FILTER_SCRIPTS also excludes the upstream per-Script
progress cursor that controls future filtering. The final PB1 never replaces
it with an upstream-compatible progress mechanism.

### 8.4 Predecessor contradiction

The D-BOOTSTRAP scratch importer does the opposite. Its shared_rows function
collects LAST_STATE, GENESIS_BLOCK, MAX_CHECK_POINT_INDEX, CheckPointIndex,
block-zero facts, and LAST_N_HEADERS. Its import path writes those rows and
also writes MIN_FILTERED_NUMBER. It includes an exact FILTER_SCRIPTS row in
the script payload.

That predecessor is more realistic about what an actual Storage instance
needs to continue, but it means the consensus-separation claim was not
demonstrated by the real-API experiment.

## 9. Package format

### 9.1 Actual artifact

The final PB1 package is a directory containing manifest.json and
payload.kvpairs. The manifest includes:

- profile_version d2-script-portability-v1;
- payload_format phroi-lc-snapshots-kvpairs-v1;
- storage_semantics ckb-light-client-keyspace-v1;
- exact referenced revisions for ckb-light-client and phroi snapshots;
- network and genesis hash;
- handoff block number and hash;
- raw Script and role;
- payload path, SHA-256 digest, and byte size;
- category row counts;
- a list of excluded authority categories.

The committed fixture payload is 743 bytes and has digest:

sha256:9f969e6492b8e2a925628e13d3e0aae91e90c8333b5e84a4295db06b651d7f73

### 9.2 Payload encoding

encode_kvpairs sorts rows by key, rejects duplicate keys, then writes a
little-endian row count followed by little-endian key and value lengths and
raw bytes. decode_kvpairs checks count and lengths, rejects trailing bytes
and non-strict ordering, and has a ten-million-row cap.

This is a reasonable deterministic test encoding. It is not a demonstrated
production package schema. It has no typed version migration layer, no
canonical manifest byte representation, and no independently authenticated
manifest.

### 9.3 Integrity and binding

The SHA-256 digest detects payload damage if the manifest is trusted. It does
not authenticate the manifest. An attacker able to rewrite both manifest and
payload can make a different valid payload appear internally consistent.
There is no signature, authenticated envelope, or key-management model.

Network, genesis, handoff, Script, and exact revision strings are compared
to caller expectations. The exact revision comparison is fail-closed but
provides no forward/backward compatibility. There is no migration policy
between light-client versions or schemas.

### 9.4 Corruption and malformed input

The decoder and isolation checks cover the cases deliberately generated by
PB1. They do not establish resistance to:

- huge allocation or decompression-style denial of service;
- malformed JSON variants beyond serde failure;
- malformed CKB packed values;
- forged transaction/header relationships;
- a manifest replacement attack;
- unknown future fields and version negotiation;
- interrupted filesystem writes;
- concurrent readers or writers.

## 10. Import and atomicity

### 10.1 Actual final PB1 behavior

load_and_validate_package validates metadata, path containment, size,
payload digest, canonical decoding, and local isolation before import.
insert_rows_atomic then starts a SQLite transaction. Existing identical keys
are treated as idempotent; conflicting values fail; new rows are inserted.
An injected fail_after count causes an error and SQLite rollback.

import_package checks that the destination authority exactly equals the
caller-supplied authority and then imports only kv_store rows. It does not
establish or update authority. It therefore depends on an already prepared
destination state.

### 10.2 Destination preconditions and merge policy

SqliteDestination::create deletes all rows and inserts the authority supplied
by the test. That is a fixture initializer, not an import precondition
contract.

The final PB1 does not establish behavior for:

- a destination with unrelated existing rows;
- a destination with the same Script at the same handoff;
- a stale destination;
- a newer destination;
- a different chain with a colliding Script;
- a different Script with overlapping row prefixes;
- duplicate import after process restart;
- partial pre-existing state followed by conflict;
- an active destination light-client process.

Exact authority equality would reject stale and newer tips in this model,
rather than define a merge or fast-forward policy.

### 10.3 Atomicity boundary

The final test proves rollback for an error injected inside one SQLite
transaction. It does not prove:

- OS-kill or power-loss durability;
- atomic import into upstream RocksDB;
- atomic import into the upstream SQLite backend;
- atomicity when import and filtering race;
- lock acquisition across processes;
- recovery from a half-written package directory.

The predecessor’s actual upstream BatchWriter does call a backend commit
that is intended to be atomic, but it was not crash-injected and it imported
global authority as well as Script state. “Fail closed” is therefore
partially demonstrated, not production-proven.

## 11. Historical replay avoidance mechanism

This is the most important failed inference in PB1.

### 11.1 What current upstream actually does

At the inspected upstream revision, the light-client filter path uses:

- FILTER_SCRIPTS metadata rows containing each registered packed Script, role,
  and its current block cursor;
- MIN_FILTERED_NUMBER, stored as a global minimum derived from those cursors;
- block-filter processing that requires the next filter range to be
  continuous from the stored minimum;
- filter_block for downloaded matched blocks;
- update_block_number after a filter range has been processed;
- LAST_STATE, LAST_N_HEADERS, checkpoints, and proof code for independent
  chain/proof progression and rollback.

The synchronizer path calls filter_block for downloaded matched blocks and
then advances Script cursors. The block-filter path advances the cursor when
there are no matched blocks. The light-client proof path can rollback
Script-derived rows and reset filtering state during a fork.

The relevant source paths are:

- light-client-lib/src/storage/storage_trait.rs:
  update_filter_scripts, update_block_number, filter_block,
  rollback_to_block, get_min_filtered_block_number;
- light-client-lib/src/protocols/filter/components/block_filters_process.rs;
- light-client-lib/src/protocols/synchronizer.rs;
- light-client-lib/src/protocols/light_client/mod.rs:
  process_last_state and commit_prove_state.

The upstream storage source is available at:
[storage_trait.rs](https://github.com/nervosnetwork/ckb-light-client/blob/12e29522ab7e078ada704d4ac04cbc0498009b7b/light-client-lib/src/storage/storage_trait.rs)
and
[light_client/mod.rs](https://github.com/nervosnetwork/ckb-light-client/blob/12e29522ab7e078ada704d4ac04cbc0498009b7b/light-client-lib/src/protocols/light_client/mod.rs).

### 11.2 What final PB1 does

The baseline calls replay_historical_script. That function explicitly loops
through fixture blocks 0 through 12 and increments a counter for every
block. It is not upstream block-filter processing and it does not read
MIN_FILTERED_NUMBER or FILTER_SCRIPTS.

The D2 path reports historical_filter_blocks_d2 = 0 as a literal result
field. The destination was created with AuthorityState already at tip 12.
The importer does not reconstruct upstream filter progress. It merely inserts
selected rows into the PB1 kv_store.

Therefore the reported 13 avoided blocks are not observed skipped upstream
filter requests. They are:

- thirteen iterations of PB1’s own replay helper for the baseline;
- zero iterations assigned to the import path by construction.

The number is reproducible as a harness counter but does not prove historical
replay avoidance.

### 11.3 Nature of the thirteen blocks

All thirteen blocks are synthetic fixture objects. Their hashes are derived
from deterministic strings. They are not mainnet, testnet, regtest, or a
real dev-chain history. Their transactions and headers are not actual CKB
wire structures.

No filter hashes, filter-chain proof, CKB header proof, block download, or
upstream scheduler request is counted.

### 11.4 Why semantic equivalence does not follow

Having the same selected rows at tip 12 is not equivalent to having advanced
the upstream light-client Script cursors safely. A real destination must
either:

- import/reconstruct the exact progress state and prove that it belongs to
  the destination’s independently established chain; or
- use a new upstream API that records a verified coverage contract and resumes
  filtering from it.

PB1 does neither.

The earlier real-API importer did set FILTER_SCRIPTS and MIN_FILTERED_NUMBER
to continue its tiny synthetic run. That is evidence that a logical
continuation can be made to work with the pinned implementation. It is not
evidence that the final consensus-free package does so.

## 12. Continuation mechanism

### 12.1 Final PB1 continuation

append_verified_block is a PB1-local helper. It checks the next block number
and parent hash, removes A cell rows if the fixture says the block spends one,
inserts the block’s A rows, inserts a verified_headers row, and updates
authority and tip in one SQLite transaction.

It reaches block 13 and leaves one live A cell. This is a coherent model
operation, not the light-client continuation path.

It does not call:

- upstream filter_block;
- upstream update_block_number;
- upstream block-filter processing;
- upstream proof validation;
- upstream rollback or reorg handling;
- a network synchronizer.

### 12.2 Predecessor continuation

The scratch importer’s post-import path uses the real upstream Storage and
calls filter_block on synthetic block 4, advances block/min-filtered state,
and updates LAST_STATE. Its result compared imported and baseline raw rows.
That is materially stronger than final PB1, but it remains an offline
single-backend experiment over a tiny synthetic chain. It does not establish
identical behavior under real peer messages, proof selection, reorgs, or
current Pocket JNI lifecycle.

### 12.3 Continuation conclusion

Post-import continuation is partially supported as a logical storage
operation. Identical behavior of an imported real light-client instance and a
normally derived real light-client instance is unproven.

## 13. Consensus separation

### 13.1 Final PB1 claim

The final manifest excludes authority rows. The destination stores authority
in tables physically separate from kv_store, and the handoff test checks that
the authority fingerprint is unchanged by import. This demonstrates a
desired model boundary:

    destination-owned authority
    +
    imported Script-derived rows

### 13.2 Why it is not enough

The authority is supplied by the test and pre-installed. PB1 never creates
that authority with the upstream verifier. Its source authority rows are
synthetic and incomplete. It also excludes the actual upstream FILTER_SCRIPTS
and MIN_FILTERED_NUMBER controls that determine whether the future Script
view is complete.

The current upstream client’s global or chain-related material includes
LAST_STATE, GENESIS_BLOCK, checkpoint rows, LAST_N_HEADERS, and matched-block
runtime state. The filter cursor and minimum filtered number sit at the
boundary between Script-derived state and chain-progress state. The clean
separation cannot be assumed merely because keys have different prefixes.

### 13.3 Direct contradiction in predecessor

The real-API scratch importer explicitly exports/imports:

- LAST_STATE;
- GENESIS_BLOCK;
- MAX_CHECK_POINT_INDEX;
- CheckPointIndex;
- LAST_N_HEADERS;
- MIN_FILTERED_NUMBER;
- FILTER_SCRIPTS.

That is not consensus separation. It is a combined snapshot of chain,
runtime, and Script-related state. It may have been the necessary shape for
that toy continuation, but it disproves the claim that the real PB1 lineage
already established a clean authority exclusion.

Overall assessment: the final model supports the design intention; the
realistic predecessor contradicts the broad claim. Consensus separation is
not proven.

### 15.2 Circular validation

The source, baseline, and expected rows share the same code-generated fixture.
The source view is selected by rows_for_selector. The baseline uses local
SQLite mutation and the same view comparison. The imported view is selected
again by PB1. This creates a closed loop in which a shared wrong assumption
can pass all three comparisons.

Examples:

- a wrong Script-family boundary can be shared by source and importer;
- synthetic transaction values can satisfy the local parser because the same
  code generated them;
- the “baseline” does not independently use upstream filter_block;
- expected digest bytes are not generated by a separate implementation;
- authority exclusion is asserted against three locally invented rows.

### 15.3 Missing tests

The harness lacks tests for:

- prefix-aliasing Scripts;
- code hash/hash type/args parsing;
- lock and type roles with identical raw bytes;
- real packed CKB transactions and headers;
- real upstream RocksDB and upstream SQLite instances;
- current and previous light-client versions;
- schema/profile migration;
- missing or extra required state;
- wrong chain with matching metadata manipulation;
- stale and newer destination tips;
- existing-state merge and conflicts across many rows;
- duplicate import after restart;
- reorg and rollback after import;
- concurrent import/filtering;
- process kill, power loss, filesystem full, or rename failure;
- large realistic Script histories;
- malformed packed values and forged header/transaction relationships;
- property/fuzz testing of package decoding;
- Android filesystem and JNI lifecycle.

### 15.4 Test-quality conclusion

PB1 has enough tests to show that its small model is internally coherent.
It does not have enough independent or system-level evidence to support the
research report’s infrastructure-level language.

## 16. Current upstream compatibility

### 16.1 Inspected upstream

The current remote develop revision inspected is
12e29522ab7e078ada704d4ac04cbc0498009b7b, with commit message
“Validate downloaded block data before indexing (#290).” The ckb-light-client
library reports version 0.5.5 in its Cargo manifest. Default native storage is
RocksDB through ckb-rocksdb 0.21.1; SQLite is an optional rusqlite 0.32
backend; IndexedDB/browser storage also exists.

The current source is linked above:
[storage directory at the exact revision](https://github.com/nervosnetwork/ckb-light-client/tree/12e29522ab7e078ada704d4ac04cbc0498009b7b/light-client-lib/src/storage).

### 16.2 Storage keyspace and APIs

The inspected keyspace has these material families:

| Prefix | Upstream meaning |
|---:|---|
| 0 | TxHash to Transaction |
| 32 | CellLockScript |
| 64 | CellTypeScript |
| 96 | TxLockScript |
| 128 | TxTypeScript |
| 160 | BlockHash to HeaderWithExtension |
| 192 | BlockNumber to BlockHash |
| 208 | CheckPointIndex |
| 224 | Meta |

The public low-level seam is StorageBackend plus BatchWriter. The high-level
LightClientStorage trait supplies default Script/filter behavior over that
seam. Native RocksDB uses a RocksDB WriteBatch; SQLite uses a transaction and
replacement semantics; the common abstraction does not make raw row import
semantically safe by itself.

This is a credible place to design an upstream-supported export/import
operation. It is not a stable package contract today. Several key constants
and raw key layouts are implementation details, and the default trait methods
assume well-formed upstream values.

### 16.3 What changed relative to PB1

PB1 depends on none of these interfaces. It reproduces prefix numbers and
some local shapes independently. It also uses a different destination model
and never asks upstream to resume filtering.

The pinned revision and the inspected current develop head happen to match,
so the basic keyspace comparison is current as of this audit. That does not
make PB1 current-compatible: exact revision strings in a manifest are a
rejection policy, not a compatibility solution.

### 16.4 Maintenance burden and better seam

A production design that imports raw rows will be tightly coupled to:

- Key encoding and suffix ordering;
- Value encodings for transactions and headers;
- FILTER_SCRIPTS and MIN_FILTERED_NUMBER semantics;
- rollback behavior;
- backend batch guarantees;
- chain-spec/genesis handling;
- version-specific storage changes.

The better seam is an upstream typed export/import or “verified Script view”
API built on StorageBackend/BatchWriter, with explicit chain/progress
contracts. That may require an upstream patch or at least upstream
cooperation. The fact that PB1 needed no patch only means it avoided the
integration problem.

## 17. Pocket Node integration reality

### 17.1 Current revision and vendor

Pocket Node inspected at:
6eda0b7a4601050b011591d41cc702f0dc7a7c38,
[exact Pocket revision](https://github.com/RaheemJnr/pocket-node/tree/6eda0b7a4601050b011591d41cc702f0dc7a7c38).

The vendored external/ckb-light-client tree is a normal tracked directory,
not a Git submodule and not a revision-pinned upstream dependency. Its
light-client-lib Cargo manifest reports version 0.5.4; its lockfile uses
ckb-rocksdb 0.21.1 and rusqlite 0.29.0. The vendor README instructs users to
build the upstream develop branch but records no exact commit. The vendor

626cf30b438ba3549290503b4a8418d3929cdbe2.

Therefore “Pocket uses the pinned current upstream revision” is not
established. It vendors a forked/copied tree with JNI additions and an older
library version number.

### 17.2 Backend and paths

The Android application rewrites configuration paths to:

    context.filesDir/data/<network>/store.db
    context.filesDir/data/<network>/network

The application has migration logic from an older flat data directory into
data/mainnet. Mainnet and testnet are isolated by directory and by the
network field in application state.

The embedded light-client database is separate from the Pocket Room database.
Room stores wallet, transaction, balance, header-cache, DAO, pending
broadcast, candidate, and sync_progress data. Importing raw light-client
rows would not by itself rebuild those application caches.

### 17.3 Script registration and restore start heights

LightClientNative exposes nativeInit, nativeStart, nativeStop,
nativeSetScripts, and nativeGetScripts. Script commands distinguish All,
Partial, and Delete. Script status contains a packed Script/JSON
representation, role, and block number.

SyncCoordinator computes fresh registration starts from sync mode:

- FULL_HISTORY starts at zero;
- RECENT uses a roughly tip-minus-200,000 window;
- CUSTOM uses a requested height;
- non-full zero results can fall back to the network checkpoint;
- candidate discovery separately chooses a historical start based on mode and
  cached transaction history.

Pocket records lightStartBlockNumber and localSavedBlockNumber in a Room
sync_progress row. SubAccountCandidateEntity records the lowest block from
which a candidate was registered. Those application records are part of
Pocket’s restore and wallet-discovery semantics, not part of the PB1 package.

### 17.4 Lifecycle insertion point

The current JNI lifecycle creates Storage, loads the chain spec, initializes
genesis state, constructs networking/protocol components, and starts
NetworkService during nativeInit. nativeStart then transitions the state to
RUNNING. There is no D2 import/restore JNI method.

The theoretically safe insertion point is after configuration and chain
spec/genesis validation, with the database closed to concurrent filtering,
and before network/filter service can consume the imported state. In the
current code, that likely requires a Rust/JNI lifecycle change or a separate
offline restore phase. Calling a raw importer after nativeStart would create a
race with the live client.

nativeStop does not make in-process network switching a general lifecycle
reset; the source comments describe process restart as the mitigation for
OnceLock state. D2 must account for this.

### 17.5 G3 assessment

G3 is architecturally credible as a future consumer:

- Pocket already embeds the relevant client;
- it already isolates network data;
- it already registers Scripts and tracks historical start choices;
- its full-history mode has a real user-visible cost.

G3 is not implementation-ready. It needs a version-pinned upstream seam,
offline import lifecycle, app-cache rebuild/reconciliation, candidate and
sync-progress policy, filesystem staging, and proof that imported coverage
does not silently conflict with Pocket’s selected start height.

The current consumer makes the D2 correctness bar higher, not lower.

## 21. Better abstraction discovered, if any

The strongest technically defensible abstraction is not generic “state
portability” and not a copy of a light-client database. It is:

    destination-owned consensus +
    source-owned, verified Script-derived view handoff

An even sharper short name is verified-view portability or Script-state
handoff. The word verified must be earned by a contract that binds:

- exact packed Script and role;
- chain/genesis identity;
- handoff header established independently by the destination;
- state rows and their typed closure;
- a truthful coverage/progress statement;
- reorg and rollback behavior;
- client-version compatibility.

This abstraction keeps the useful D2 boundary while exposing the unresolved
fact that progress state may be a first-class part of the handoff contract.
It should not be described as arbitrary database migration.

## 22. Future, not v0.1

The following should remain out of the first proof:

- cross-version state migration;
- public snapshot distribution or third-party state providers;
- cloud backup;
- generic blockchain database migration;
- wallet-sync product behavior;
- multi-chain generalization.

They are not needed to decide whether a safe, source-to-destination
Script-derived view handoff is possible.

## 23. Recommended next gate

Do not begin G1 implementation in this project yet. The next gate should be
a narrowly scoped reproof plan with these acceptance conditions:

1. Use the inspected upstream ckb-light-client revision as an actual
   dependency or a temporary linked checkout. Instantiate real upstream
   RocksDB and SQLite Storage.
2. Build a real packed CKB fixture with enough blocks to cover creation,
   spend, replacement, unmatched blocks, lock/type role differences, and a
   fork/rollback case. Synthetic chain bytes are not sufficient.
3. Derive the baseline through ordinary upstream registration,
   block-filter processing, filter_block, proof/state progression, and
   query APIs. Implement the package extractor independently from the
   baseline comparator.
4. Decide explicitly whether FILTER_SCRIPTS and MIN_FILTERED_NUMBER are:
   - transported as typed Script-progress state;
   - recomputed from a stronger coverage proof; or
   - excluded, with the destination required to rescan a defined interval.
   There is no safe fourth option where the destination simply assumes
   historical work was done.
5. Test exact packed Script identity, role, key boundaries, shared
   transaction/header closure, and unrelated Script exclusion.
6. Test destination preconditions, stale/newer handoffs, repeated import,
   pre-existing rows, conflicts, reorgs, and cross-backend behavior.
7. Add process-level crash/kill tests and backend-specific durability tests.
8. Measure realistic histories and package/import cost before calling the
   result infrastructure.

Only after those pass should G3 evaluate the Pocket JNI lifecycle and Android
staging. Pocket integration should consume a supported import/restore seam,
not force the app to manipulate a raw database while NetworkService is live.
